Enforcement

Three checks in one place

A hook inside the agent evaluates every action against your policy — deny-by-default, fail-closed.

  • Protected paths

    Writes to configuration, policies, CI and agent setup are blocked. It accounts for common bypasses such as symlink targets and manifest/lockfile detours — no guarantee, and not a sandbox replacement.

  • Dangerous commands

    Shell actions are checked against your rules before they run. Known bypasses via loader variables such as LD_PRELOAD are accounted for.

  • Dependencies

    New packages only from your allowlist. Installs that can't be verified are rejected fail-closed — the same in the hook and the MCP tools.

Honestly scoped. TollWire is not a replacement for a sandbox and does not replace an audit. It is an additional, verifiable control layer (defense-in-depth) run together with an isolation environment. The plugin code makes no network requests.

Flow

How it works

Four steps, local. TollWire itself runs on your machine and sends neither code nor prompts anywhere.

  1. Intercept

    The agent is about to write a file or run a command — the hook intercepts the action first.

  2. Check

    Paths, commands and dependencies are checked against your policy (deny-by-default).

  3. Decide

    Allowed → it goes through. Violation → blocked with a clear reason and exit code.

  4. Record

    The decision is written to a hash-chained log — tamper-evident and verifiable.

Architecture

How TollWire steps in

TollWire sits as a PreToolUse hook between the agent and the system. Every action passes the policy before it takes effect — and is logged.

Evidence

Records, not chat logs

Changes, reviews, scans and approvals are mapped — as a draft, not audited — to controls from ISO/IEC 27001 and NIS2. TollWire provides evidence; it does not replace an audit or a certification.
